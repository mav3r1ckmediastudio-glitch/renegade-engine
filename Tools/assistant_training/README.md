# Living Core character experiments

These scripts produce isolated adapters and comparisons. They never deploy, overwrite the original adapter, change the approved orb/voice or expose editor mutation tools.

The first V4 experiment continued V3.1 using the original 20 four-turn scenarios: 64 authored training continuations, 64 older social/correction replay records and 16 held-out continuations. It failed behavioural review; the preserved output manifest pins that older corpus hash.

The V6 corpus has 36 four-turn scenarios, including explicit user/engine name distinction, fictional memory clarification, music continuity and correction handling. Four entire scenarios (origin, boat, music and lights) remain held out, giving 128 authored training continuations and 16 held-out continuations. --fresh-base starts a new rank-8 adapter from the cached base model and excludes old replay entirely; it uses learning rate 5e-5. Default continuation mode adds 64 selected older records and uses learning rate 2e-5. Neither mode downloads weights. The manifest records the exact corpus hash and split.

Run train_character_candidate.py with --lab pointing to the existing conversation lab and --output pointing to a fresh experiment directory. --prepare-only creates the dataset without loading a GPU model. Each row trains only its final assistant answer; exact chat-template prefix boundaries are checked, examples over 768 tokens are rejected rather than truncated. Trusted user names, where supplied by a scenario, are appended to that scenario's system identity. Whole-scenario splitting prevents earlier held-out turns leaking into training.

Run evaluate_character_candidate.py with --lab and --candidate. It compares old/candidate adapters using equal decoding settings, seeds and each adapter's own generated history. Expected reference replies are retained for review and never fed back. --clean-character uses a compact shared character prompt without the service's technical-support layer; default uses the actual current service/persona combination. Results under different prompt modes must not be presented as a weights-only comparison.

The separate diagnose_clean_character.py compares V3.1 and adapter-disabled base under a clean prompt. The ignored ablation script compares the existing combined service prompt, shorter added persona and base without replacing live defaults. These are diagnostics, not accepted replacements.

Review relevance, identity, fiction clarity, continuity, repetition, correction handling, name/role distinction and operational truthfulness. Do not require the model to reproduce the reference story: a follow-up referring to an unintroduced character is not a fair independent correctness test. Loss and compilation alone do not establish quality. Recheck source-backed guides separately and require owner conversation/voice review before closing character acceptance.

## Day 1 continuation corpus, 2026-10-15
character_day1.json contains100 newly authored three-turn conversations:60 casual,12identity,9lore,4truth and15engine. These are supervised training references, never runtime response scripts. Casual topics deliberately extend beyond the workshop. Identity-after-chat and refusal recovery address observed owner failures; explicit source-vs-fiction boundaries and ordinary British phrasing remain. Names vary across examples, including alphanumeric handles; no general spoken-name framework is implied.
Technical content is limited to existing verified Surface Type and spawn-point guidance or conversational evidence/access policies. Source references are recorded per engine scenario. Surface guidance is source/native-test checked; visual release acceptance remains separate. The existing runtime verified-guide route remains authoritative for technical steps.
train_character_day.py continues the preserved V6 adapter against its exact pinned base snapshot. It requires a fresh output directory, checks base/adapter compatibility, records source SHA256s and verifies the original adapter is unchanged after training. It creates300 new final-answer training examples and replays128 original V6 examples, with16 whole-conversation held-out examples. Shared character lore is intentionally present in the system prompt; held-out loss is not a test of unknown factual knowledge. A separate character_day1_evaluation.json defines36 independently worded user prompts; the current benchmark appends4backstory prompts, for40 free-running turns. Prompts cover identity in context, names, fiction consistency, preferences, selection access, topic changes and Surface Type boundaries. No reference assistant replies are fed into that evaluation history.
The initial schedule is107 optimiser steps, gradient accumulation4, batch1, learning rate1e-5, rank/alpha inherited from V6, one pass over428 training rows. Every example is tokenised and its assistant label boundary checked before GPU loading. Input over1024tokens is rejected rather than truncated; first preflight maximum629tokens. --prepare-only writes inspectable train/heldout manifests without loading GPU weights. No recurring training task or automatic candidate deployment is configured. Compare with the current V6 Q5 runtime at the same0.65adapter strength and retain the baseline unless semantic and owner review support a replacement.


### Refusal recovery experiment (15 October)

Owner live testing rejected V7 Day1: harmless joke requests received refusals and were wrongly classified as fictional past events. V6 also reproduces this under refusal-bearing histories; clean-start successes are insufficient. Do not redeploy V7 on the strength of the earlier40turn evaluation.

`character_recovery.json` contains20 correction examples. Each preceding bad assistant answer is context only. `train_character_recovery.py` trains only the final correct assistant continuation, using the same exact chat-template prefix masking as the Day1 trainer, plus128 V6 replay answers and16 separate original held-out rows. Default74steps/batch1/accum4 means two passes over148 examples at1e-5. Source adapter is V6; output must be fresh. No prompt change or runtime joke lookup is introduced. Recovery dataset SHA256 fef42553a660d25480b6513a6882897fd3689a9706f8d27896624679a6961190.

`evaluate_character_recovery.cjs` probes8 independent contexts at3 seeds (24 replies), including previous bad refusals, lore-to-humour transitions, prior-session uncertainty and editor-boundary-to-play transitions. It calls the local raw backend to test learned behaviour. `RECOVERY_RESULTS` chooses a BUILD output filename. Its keyword flags are only triage: manually review every reply for evasions, false denials and coherent fulfilment. Benchmark prompts/answers are not supplied as training targets. Run broad existing character evaluation as well before proposing an owner trial. An experiment may fail; retain baseline and evidence rather than script over the symptom.
