# LP06 Gate 2 — Clean Loose Cooker and Governed Staging

## Baseline

Gate 2 starts from accepted LP06 Gate 1 on merged `main`:

- Renegade: `ca97b05988ed6f8100b83ac8921873f333bf40bb` (PR #40)
- Wicked: `3a800b7134aafe58461093c8abb2e274d4e64033`

Gate 1 remains the authority for the named Windows build plan. Gate 2 consumes
that plan; it does not rediscover dependencies, reimport assets, or broaden the
Runtime support allowlist.

## Outcome

Materialize the exact Gate 1 plan into a unique loose staging tree that is
safe to inspect and deterministic to rebuild. The stage is deliberately not an
owner-visible final build and is not yet claimed to launch independently.

## Contract

`BuildStageService` must:

1. create a single-use staging directory below
   `<output-parent>/.renegade-staging/`, sharing the final build's parent and
   therefore its volume;
2. leave `<output-parent>/<Game Name> Windows Build/` untouched;
3. copy only project files named by the Gate 1 plan;
4. recompute project FNV-1a content identity before copying and fail if source
   bytes changed after planning;
5. accept exactly one authoritative source for every Gate 1 Runtime-support
   entry, then verify byte count and SHA-256 before and after copy;
6. accept only the current governed package-document set and require each input
   to carry version-controlled (`repo:`) or pinned (`pinned:`) provenance;
7. generate canonical project, content, Runtime-support and package manifests;
8. generate a deterministic build-component inventory and a stage-only build
   report;
9. record normalized package-relative path, byte count, SHA-256, class and
   provenance for the staged file set;
10. re-enumerate and re-hash the completed stage and reject extras, missing
    files, symlinks, case-equivalent destination collisions or tampering.

The root package manifest lists every other staged file and explicitly declares
that its own hash is excluded from its self-referential file array. The stage
result separately records the package-manifest SHA-256 for evidence.

## Current governed package-document set

Gate 2 requires these version-controlled inputs:

```text
ReadMe.txt
Licences/Renegade-Licence-or-Notice.txt
Licences/WickedEngine-LICENSE.txt
Licences/WickedEngine-third_party_software.txt
Licences/DirectXShaderCompiler-LICENSE.txt
Licences/DirectXShaderCompiler-ThirdPartyNotices.txt
```

`Licences/Build-Component-Inventory.txt` is generated by Gate 2.

The CTest fixtures contain explicit **test placeholders only**. They prove the
copy/provenance/manifest mechanism and are not legal redistribution notices.
A public distributable remains blocked until real pinned notice text, a
Renegade product licence/notice policy, and the selected Visual C++ deployment
policy are supplied and proven.

## Acceptance matrix

Gate 2 is a candidate only when all of the following pass on the exact head:

- valid staging succeeds with a project/output path containing spaces and
  non-ASCII text;
- the final owner-visible build directory is not created or modified;
- an unused project file outside the Gate 1 plan is absent from staging;
- all required content/support/manifests/notices/inventory/report are present;
- machine-specific absolute paths do not enter normalized manifest bytes;
- reordering equivalent Runtime/document inputs produces byte-identical
  normalized manifest JSON and hashes;
- reusing a staging ID fails closed;
- a missing Runtime source fails closed;
- a missing notice input fails closed;
- Windows case-equivalent notice collisions fail closed;
- project bytes changed after planning fail closed;
- Runtime support bytes changed after planning fail closed;
- injected extra staged content is rejected;
- tampered staged content is rejected;
- a missing governed staged file is rejected;
- complete Debug and Release CTest pass, including
  `RenegadeBuildStageTests`;
- pinned-Wicked Debug and Release baseline checks remain green;
- independent exact-head review reports no blocking defect.

## Gate 2 exclusions

Gate 2 does **not**:

- rename or resource-stamp `RenegadeRuntime.exe`;
- add package-relative Runtime bootstrap behaviour;
- launch the staged executable;
- claim DX12/Vulkan standalone behaviour;
- choose or deploy the Visual C++ Runtime;
- publish, replace or atomically promote an owner-visible build;
- preserve/replace last-good output (Gate 5);
- create an archive or protected/encrypted package;
- alter Studio UI;
- modify Wicked or its pin.

Those boundaries keep Gate 2 focused on the loose deterministic cooker and
staging proof required before LP06 Gate 3.
