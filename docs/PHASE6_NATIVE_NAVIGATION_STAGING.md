# Phase 6 Native Navigation — Staging

## Purpose

This staging branch establishes Renegade navigation on Wicked Engine's native
`VoxelGrid`, `PathQuery`, and `CharacterComponent` facilities. Renegade does not
introduce Recast/Detour, a second navmesh, or another actor-navigation world in
this Phase 6 slice.

The long-term product direction remains deliberately open to a later surface
navmesh for high-quality ground-only AI. That would complement, not replace,
Wicked voxel navigation for flying, swimming, climbing, volumetric and dynamic
navigation use cases.

## Native Wicked baseline

The Renegade Wicked pin is `3a800b7134aafe58461093c8abb2e274d4e64033`.
At that pin:

- `wi::VoxelGrid` owns the generated occupancy grid and serializes through Wicked;
- `Scene::VoxelizeScene()` injects matching Scene geometry into a VoxelGrid;
- `wi::PathQuery::process()` performs pathfinding on that VoxelGrid;
- grounded PathQuery traverses occupied ground voxels with empty clearance above;
- flying PathQuery traverses empty voxels in full 3D;
- `CharacterComponent::SetPathGoal()` stores a goal and VoxelGrid pointer and
  defers native path processing to the normal Wicked Scene update; and
- Wicked's own character-controller example consumes the next PathQuery waypoint
  and drives `CharacterComponent::Turn()` / `Move()` toward it.

Renegade follows that native split. `SetPathGoal()` is not treated as an actor
movement API and Renegade does not move navigation actors by overriding their
Transforms every frame.

## EngineBridge implementation

`NavigationService` remains an adapter over native Wicked data. It provides:

1. bounded creator-facing grid generation settings;
2. creation of one persistent Scene entity carrying Wicked's serialized
   `VoxelGrid` component;
3. rebuild through `Scene::VoxelizeScene()` using navigation/collider filters;
4. synchronous start-to-goal `PathQuery` results for creator preview/tests;
5. native `CharacterComponent::SetPathGoal()` handoff;
6. persistent agent-to-grid and agent-to-destination references using Renegade
   entity IDs rather than transient ECS entity numbers;
7. native next-waypoint following through `CharacterComponent::Turn()` and
   `CharacterComponent::Move()`;
8. lightweight Runtime binding/repath state without a competing navigation
   simulation; and
9. command-backed grid and test-agent creation for normal Undo/Redo/dirty-state
   behaviour.

The default generation filter is:

`FILTER_NAVIGATION_MESH | FILTER_COLLIDER`

This follows Wicked's own character-controller navigation pattern and avoids
silently treating every decorative render mesh as walkable/navigation geometry.
Terrain generated by Wicked already carries the navigation-mesh filter.

## Creator authoring slice

The Renegade Navigation specialist Inspector is integrated into the Scene ADD
menu and hierarchy selection routing. The creator surface now provides:

- **ADD -> NAVIGATION GRID** for a persistent native Wicked VoxelGrid entity;
- editable X/Y/Z resolution controls;
- a uniform voxel-size control in metres;
- **REBUILD GRID** using current terrain/navigation meshes and colliders;
- **FIT TO SCENE + REBUILD**, preserving a uniform voxel size and automatically
  increasing it when needed to remain within the bounded grid limits;
- **SHOW NAVIGATION VOXELS**, using Wicked's own `VoxelGrid::debugdraw()`;
- **CREATE TEST AGENT + TARGET**, creating a visible authoring agent with a
  native Wicked `CharacterComponent` plus a linked destination marker;
- **REFRESH PATH**, running Wicked `PathQuery` from the authored agent to target;
  and
- **SHOW QUERIED PATH**, drawing the returned native waypoint chain in the editor
  viewport.

Grid, agent and destination selections all retain the specialist Navigation
Inspector. The agent is deliberately inactive while authoring so moving markers
with Renegade's normal gizmo cannot make it wander or fall in Studio.

## Runtime/Test Level proof

When Test Level loads an authored navigation pair, Runtime resolves the saved
persistent grid/destination references, activates the existing native Wicked
`CharacterComponent`, submits its goal to the linked native VoxelGrid and then
consumes `CharacterComponent::pathquery.get_next_waypoint()` on subsequent
frames. Direction is handed back to Wicked through `Turn()` and `Move()`.

Runtime also publishes navigation synchronization, discovered-agent count and
arrival count through the existing live diagnostic endpoint. This gives owner
and CI diagnostics a way to distinguish "the level loaded" from "the authored
navigation binding was actually discovered".

The focused CPU-side regression now covers grid creation/rebuild Undo/Redo,
grounded and flying PathQuery, persistent authoring-reference resolution,
Runtime native-grid handoff and issuance of native CharacterComponent movement.
A source contract locks the Studio controls, specialist routing and Runtime
integration tokens so they cannot silently disappear from a later refactor.

## Owner acceptance

For the first visible proof:

1. open a level containing terrain/floor and at least one obstacle;
2. choose **ADD -> NAVIGATION GRID**;
3. use **FIT TO SCENE + REBUILD** (or tune the grid manually);
4. click **CREATE TEST AGENT + TARGET**;
5. move the agent and target with the normal gizmo so both sit on walkable areas,
   preferably on opposite sides of the obstacle;
6. press **REFRESH PATH** and confirm the displayed path routes around the
   obstacle;
7. save the level and run **Test Level**; and
8. confirm the visible test agent follows the route toward its destination.

This is deliberately a creator-visible proof surface, not the final NPC UX.
Real imported characters can be bound to the same native service in a later
actor-authoring gate without replacing the navigation foundation.

## Remaining after this slice

The branch does not claim the complete future AI/navigation product. Remaining
work after this acceptance slice includes polished binding of real imported NPC
assets, creator-facing tuning for agent radius/height/speed and behaviour,
optional governed Lua path/agent APIs where stock actor behaviour needs them,
advanced dynamic/rebuild policies, and any later surface-navmesh complement that
proves worthwhile.

This branch should receive one exact-head Windows CI run followed by the owner
acceptance above; avoid speculative rebuild cycles.
